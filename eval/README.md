# 고정 입력 반복 평가

세 가지 개선을 반복 실행하고 대상 선택·필요 매뉴얼 조회·응답 지연을 집계한다.
평가 실행은 웹 서버와 분리되어 있으며 `session.db`나 실행 중인 서버를 변경하지 않는다.
추가 패키지나 API 키 없이 기존 `.venv`를 사용한다.

## 바로 실행

프로젝트 폴더에서:

```bash
# 기본 제공 커밋과 현재 코드 비교. 모의 모델, 14개 사례, 사례별 3회 측정.
bash sh/run_eval.sh

# 실제 로컬 Ollama. 먼저 ollama serve와 모델 두 개가 준비되어 있어야 한다.
# 반복 실행이므로 단일 채팅보다 시간이 오래 걸릴 수 있다.
bash sh/run_eval.sh --backend ollama --case web_auth --case unknown_service --repeats 3 --warmups 1 --timeout-seconds 60

# 현재 코드만 평가
.venv/bin/python3 -m eval.run_eval --backend fake --repeats 3 --warmups 1

# 다른 커밋과 비교
.venv/bin/python3 -m eval.run_eval --baseline-ref 741cd7e --backend fake
```

`sh/run_eval.sh`의 기본 비교 대상은 교수님 기본 파일을 저장한 실제 Git 커밋 `741cd7e`다.
v1 선형 파이프라인이나 임의로 흉내 낸 이전 동작을 baseline으로 사용하지 않는다.
Git 기록에서 `agent/`, `data/`만 임시 디렉터리로 읽어오고 두 코드를 별도 Python 프로세스에서 실행한다.
현재 작업 트리를 reset/checkout하거나 `.git`을 수정하지 않는다.

## 결과 파일

매 실행마다 `doc/eval_runs/<실행시각>_<ID>_<모델모드>/`를 새로 생성한다.
`--output-dir <새 폴더>`로 지정할 수도 있다. 기존 결과 폴더를 덮어쓰지 않는다.

- `report.md`: 발표용 요약 표와 계산식·주의사항
- `summary.json`: 전체 및 질문별 점수·중앙값·표본 수, 모델 이름, 커밋, 소스 파일 해시
- `results.csv`: 측정한 각 turn의 기대 대상, 실제 대상, 점수, 지연, 오류
- `raw_results.jsonl`: 워밍업을 포함한 실제 답변·조회 이력·실행 이벤트
- `dataset.json`: 이 실행에서 사용한 고정 데이터와 정답 사본

모델 호출 실패·제한 시간 초과도 원시 결과와 점수에 남는다.
`--timeout-seconds`는 여러 turn을 포함한 사례 전체의 제한 시간이다. 초과하면 해당 사례의 turn을 모두 실패로 기록한다.
실행 상태(`complete`, `interrupted`, `failed`)를 요약과 보고서에 남긴다.
중단·실패한 실행은 일부 측정만 남을 수 있으므로 완료된 전체 비교로 해석하지 않는다.
워밍업은 원시 기록에 보관하지만 집계 점수와 중앙값에서 제외한다.
고정 fixture의 조회 시각은 실제 운영 관측 시각이 아니다.

## 지표 정의

### 대상 선택 정확도

기대 route와 실제 모니터링 대상 집합이 모두 일치한 turn 수 / 전체 측정 turn 수.
미등록·대상 누락 사례는 조회하지 않는 것에 더해 정답에 지정한 확인 안내 문구도 검사한다.
단순히 아무 도구도 호출하지 않거나 일반 대화로 빠진 경우를 정답으로 처리하지 않는다.
집합으로 비교하므로 조사 순서는 무관하고, 불필요한 서비스가 추가되면 오답이다.

### 필요 매뉴얼 조회 재현율

기대한 매뉴얼 유형 중 실제로 성공적으로 읽은 유형 수 / 기대 유형 수.
같은 유형의 중복 조회를 여러 번 정답으로 세지 않는다.
예를 들어 CPU와 메모리 두 유형이 필요한데 CPU만 읽으면 1/2이다.

이 지표는 **매뉴얼 조회 단계의 유형 재현율**이며, 답변 전체의 정확도·검색 순위 지표·
서비스별 권고 연결률은 아니다. 서비스별 권고 연결은 기존 자동 테스트로 별도 확인한다.
필요 매뉴얼이 없는 정상·일반 대화 turn은 재현율 분모에 넣지 않고, 분모가 전부 0이면 N/A로 표시한다.
불필요한 매뉴얼을 읽는 문제는 `unexpected_manual_count`, `manual_exact_turns`와 사례별 원시 결과로 확인한다.

### 응답 시간 중앙값

각 turn의 그래프 호출 시작부터 최종 결과 반환까지 걸린 시간의 중앙값이다.
실패 turn은 시간 중앙값에 넣지 않지만 실패 수와 유효 시간 표본 수를 함께 표시한다.
실패를 정확도 분모에서 제외하지 않으며, 전부 실패하면 시간을 0초로 표시하지 않는다.
전체 중앙값은 이 평가 질문 묶음의 값이고, 질문별 중앙값도 `per_case`에 제공한다.

프로세스 시작, 그래프 구성, 워밍업은 시간에서 제외한다.
기존 코드에 포함된 태스크당 0.35초 인위적 지연은 포함한다.
실제 모델의 캐시·내부 추론 변동을 완전히 통제하지 못하며, 모델의 temperature=0도 완전한 결정론을 보장하지 않는다.
반복마다 이전/현재 코드의 실행 순서를 바꿔 한쪽을 항상 먼저 실행하는 영향을 줄인다.

## 고정 사례

`cases.json`에 14개 시나리오, 총 15개 turn의 기대 결과를 명시했다.
정답은 평가 데이터에 사람이 지정하며 `classify_incidents()`로 자동 생성하지 않는다.

| case ID | 확인 내용 |
|---|---|
| payments_cpu | CPU 매뉴얼 |
| cache_memory | 메모리 매뉴얼 |
| log_disk | 디스크 매뉴얼 |
| gateway_timeout | 네트워크 타임아웃 매뉴얼 |
| auth_latency | 응답 지연 매뉴얼 |
| healthy_web | 정상 서비스의 불필요한 매뉴얼 방지 |
| payments_cache | 서로 다른 두 매뉴얼 조회 |
| web_auth | 정상 서비스와 저하 서비스 구분 |
| one_service_two_types | 한 서비스의 두 장애 유형 |
| unknown_service | 미등록 서비스 안내 |
| missing_target | 대상 서비스명 되묻기 |
| clarify_followup | 확인 질문 후 서비스명만 답하는 2-turn 대화 |
| greeting | 일반 대화 유지 |
| mixed_unknown | 정상 등록명과 미등록 이름이 함께 있는 요청 |

## 비교 범위와 한계

- 데이터 수집은 고정 MCP fixture 어댑터를 사용한다. 실제 모니터링·MCP subprocess 전송·웹 지연은 측정하지 않는다.
- `fake`는 제공된 모의 분류·계획·보고 모델을 사용한다. 실제 언어 이해 성능이나 실제 LLM 속도로 해석하면 안 된다.
- `ollama`는 실제 로컬 모델을 사용하지만, 관측 데이터는 여전히 고정 fixture다.
- 샘플 수와 범위가 제한된 회귀 평가다. 전체 운영 장애에 대한 정확도나 일반적인 속도 향상을 주장하지 않는다.
- 오류·시간 초과가 있으면 그 수와 해당 사례를 먼저 확인한다. 부분 성공의 중앙값만으로 더 빠르다고 판단하지 않는다.
- LLM-as-judge, 실행 승인 노드, 실제 복구 조치는 이번 추가 범위에 포함하지 않는다.
- 과거 커밋과 현재 코드를 현재 설치된 같은 Python 패키지 환경에서 평가한다. 과거 패키지 버전까지 복원하는 실험은 아니다.

평가 도구 자체의 검증도 기존 자동 테스트에 포함한다:

```bash
.venv/bin/python3 -m unittest discover -s tests -v
```
