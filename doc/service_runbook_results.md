# 개선 3: 서비스별 장애 매뉴얼 조회와 권고 대상 표시

## 문제

복수 서비스의 알림을 합쳐 매뉴얼 하나만 고르므로 payments-service의 CPU 문제와
cache-service의 메모리 문제를 동시에 요청해도 CPU 매뉴얼만 제공했다.
보고서의 전체 항목 수 제한 때문에 여러 매뉴얼을 수집하더라도 특정 서비스가 빠질 수 있었다.
권고의 대상 서비스명도 명시하지 않았다.

## 변경

- 서비스별 관측값·알림으로 필요한 장애 유형을 모두 분류한다.
- 매뉴얼 원문에 서비스명·장애 유형을 연결하여 수집한다.
- 서비스·매뉴얼마다 최소 한 개, 최대 세 개의 항목을 제공한다.
- 모델이 특정 매뉴얼의 항목을 누락하면 모든 매뉴얼의 기본 원문 항목으로 대체한다.
- 권고와 진행 상태에 대상 서비스명을 표시한다.
- 현재 정상이고 분류할 징후가 없으면 장애 매뉴얼 대신 현재 관측의 한계와 과거 이력 확인 필요성을 안내한다.
- 같은 매뉴얼을 여러 서비스에 적용할 때는 조사 단계에서 원문 조회를 공유한다.

## 전후 비교

| 고정 입력 | 이전 | 개선 후 |
|---|---|---|
| payments-service + cache-service | CPU 매뉴얼만 조회 | payments-service → CPU, cache-service → 메모리 |
| web-01 + auth-service | 응답 지연 매뉴얼, 대상 서비스 표시 없음 | auth-service → 응답 지연. web-01은 현재 관측에서 분류할 징후가 없음을 안내 |

`service_runbook_comparison.json`은 사용자 테스트와 같은 고정 수치를 넣고
결정론적 모델로 그래프 전체를 실행한 비교다. 모델 성능이나 응답 시간 비교는 아니다.
`service_runbook_live_checks.json`은 실제 Ollama 모델과 MCP를 사용한 별도 검증이다.
실제 검증에서도 두 사례의 매뉴얼 연결이 위 표와 일치했고, payments/cache의 모델 선택은
누락에 따른 기본 보고서 대체 없이 통과했다. web/auth는 스트리밍 경로로 확인했다.

자동 테스트는 기존 대상 확인·근거 보존을 포함해 32개 통과했다.
같은 매뉴얼의 중복 조회 방지, 한 서비스의 복수 증상, 선택 누락 시 대체,
정상·분류 불가 사례, 재계획 시 중복 방지도 검사했다.

## 한계

- RAG가 아닌 키워드·수치 규칙 기반 분류로, 새로운 표현이나 장애 유형은 추가 대응이 필요하다.
- 매뉴얼 선택과 원문 보존이 근본 원인이나 공통 원인을 확정해 주지는 않는다.
- 매뉴얼이 많아지면 입력량과 보고서 길이가 늘어난다.
- 현재 정상이라는 관측으로 과거 급증이 없었다고 단정하지 않는다.
