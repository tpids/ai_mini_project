# 개선 2: 수집 근거와 매뉴얼 조건을 보존하는 대응 보고

## 문제와 원인

수동 테스트에서 일회성 CPU 관측을 근거로 조건 없이 증설을 권고하거나,
느린 인스턴스명을 새로 추가할 인스턴스처럼 표현하는 답변이 나왔다.
또한 모델의 `특이 패턴 없음`을 로그 조사 결과처럼 표현할 수 있었다.
기존 검증은 길이와 `1)` 번호만 확인했고, 세 번 실패하면 초안을 강제로 통과시켰다.

## 변경

- 관측 수치와 알림을 직접 표시하고, 매뉴얼 임계값과 구분한다.
- 지속 여부·로그·배포·리전 분포·근본 원인의 미확인을 명시한다.
- 모델은 관련 매뉴얼 항목 ID를 최대 세 개 선택한다. 최종 권고는 해당 원문을 그대로 사용한다.
- 보고서의 원문 일치를 검사하고, 실패한 초안을 스트리밍하지 않는다.
- 선택 실패 또는 재작성 한도 도달 시 임의 내용 대신 원문 기반 기본 보고서를 제공한다.

## 검증

`evidence_report_comparison.json`에 동일한 고정 관측값·매뉴얼을 사용한
Ollama qwen3:8b의 개선 전후 답변과 실제 선택 항목을 보관했다.

| 사례 | 개선 전 실제 관찰 | 개선 후 |
|---|---|---|
| payments-service CPU | 반복 호출·배치 작업의 특이 패턴이 없다고 확인한 듯 표현 | 최근 로그가 수집되지 않았음을 명시 |
| payments-service CPU | CPU 지속 조건은 이 회차에서는 유지됨 | 선택된 3번 항목의 `90%를 넘고 지속되면`을 원문 그대로 보존 |
| auth-service 응답 지연 | 알림 수치와 매뉴얼 권고를 함께 서술 | 알림 원문·미확인 사항·조건부 매뉴얼 원문을 분리 |

두 사례 모두 모델이 유효한 항목 ID를 선택했고 기본 항목으로 대체하는 경로는 사용하지 않았다.
개선 후 원문 일치 검증은 두 사례 모두 통과했다. 두 건의 결과를 일반적인 정확도 비율로 해석하지 않는다.
고의로 잘못된 수치·조건·ID를 넣는 경우, CPU가 90% 미만인 경우,
매뉴얼이 없는 경우, 연속 검증 실패와 기존 대상 확인 기능은 자동 테스트로 검증했다.

| 고정 입력 | 개선 전 생성 시간 | 개선 후 생성 시간 |
|---|---:|---:|
| CPU | 26.25초 | 79.38초 |
| 응답 지연 | 32.42초 | 43.58초 |

각 조건 한 번씩 측정했다. 캐시·모델 로드·내부 추론의 영향을 통제한 성능 실험이 아니며,
이번 기록에서는 개선 후가 더 느렸다. 속도 향상을 성과로 주장하지 않는다.

실행 방법: `.venv/bin/python3 -m unittest discover -s tests -v`

## 한계와 트레이드오프

- 자유로운 설명 대신 정형적인 보고서와 원문 인용을 사용해 답변이 길어진다.
- 원문의 보존은 보장하지만, 잘못된 매뉴얼이나 부적절한 항목 선택까지 해결하지는 않는다.
- 시계열·로그를 추가 수집하거나 실제 복구 조치를 실행하지 않는다.
- 진단 답변은 검증 후 표시하므로 작성 중 토큰은 보이지 않는다. 진행 상태는 계속 표시한다.
- OpenAI 경로는 모의 응답으로 공통 로직을 검증했으며 유료 API는 호출하지 않았다.
